## Highlights
- Coding agents send the whole conversation again on every turn. Prefix caching keeps the inference engine from redoing that work, but only if the harness leaves the start of the prompt alone and the engine sends each turn back to the GPU that already has it cached. Together AI and Ollama work on opposite sides of that handoff, so we wrote down what each, the client side and the inference engine side, needs to do to successfully build agentic apps. ([View Highlight](https://read.readwise.io/read/01m7r2wqbwtsgmhrwpvtb31rvv))
- Coding agents have an odd traffic pattern. Every time the agent takes a step, the harness sends the model the entire conversation so far: the system prompt, every tool definition, your request, every file the agent has read, and every command it has run. What comes back is usually a tool call a few dozen tokens long. Then it happens again, with everything from last time plus a little more. ([View Highlight](https://read.readwise.io/read/01m7r2wvf5q6q1pk3rk8kk8xzr))
- This large input sequence length (ISL) and small output sequence length (OSL) is characteristic of most agentic workloads. If the GPU had to work through that whole transcript from scratch on every turn, long sessions would get slower and more expensive with every step. **Prefix caching** is what saves most of that work. The problem is that if you’re not careful it's also very easy to break the prefix cache. ([View Highlight](https://read.readwise.io/read/01m7r2x2nda6bq08jenzczr8gh))
- We come at this problem from opposite ends. Ollama works on harness integrations which means deciding what goes into each request. Together AI works on the inference engine which means deciding what happens when that request arrives. We kept finding that much of our work on each side is about protecting the cache from things the other side can do to it, so we wanted to write it all down in one place to help agent and infra builders alike! ([View Highlight](https://read.readwise.io/read/01m7r2xaqty5wbn04m6gsw2hx6))
- Every request goes through two phases. The first is prefill: the engine reads the whole prompt in one big parallel pass and produces the first token. GPUs are good at this because it's a lot of math done all at once which maximizes arithmetic intensity. Prefill determines how long you wait before any new tokens appear. The second is decode: the model writes the rest of the answer one token at a time, and each new token requires reading back and attending through everything before it. Decode is limited by memory bandwidth more than by compute, and it determines how fast the text streams out. ([View Highlight](https://read.readwise.io/read/01m7r2y4yfneba389jjs0c22ns))
- A normal chat response spends time in both phases while an agent turn is mostly prefill, because the input is the whole session and the output is usually a short tool call. Reasoning models add thinking tokens on top of that, sometimes a lot of them, but as a session grows into the tens of thousands of tokens the input still dominates. Each turn the input gets longer, and the output stays roughly the same size — a few tool calls. ([View Highlight](https://read.readwise.io/read/01m7r2yyfvfk24b2tnf8ccymdh))
- The easiest way to picture the KV cache(or even the prefix cache, for that matter) is reading. Imagine that to read each new word on a page, you had to start again from the top. The further down the page you got, the slower you'd go, because you'd keep having to reread everything you'd already read. That's a model with no cache. The cache solves this within a single request: the engine keeps the work it did on earlier tokens(stored as intermediate key, value pairs) and computes only the new one. ([View Highlight](https://read.readwise.io/read/01m7r2z3hgpyjjan4en7r4wqf7))
- Prefix caching does the same thing across requests. Turn 7 of an agent session is turn 6 plus a bit more, so if the engine still holds turn 6's work, it only has to process the new part.
  ![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6af7a0c59830f120ed9f25b8_image%203.webp) ([View Highlight](https://read.readwise.io/read/01m7r2zgaz065422t9czxr2y18))
- Adding to the end of the prompt costs nothing extra. Changing anything earlier, even a single character, means re-processing everything after it. If the change is near the top, you've effectively thrown away the whole session and now must rebuilt the cache. Almost everything else in this post follows from that one rule. ([View Highlight](https://read.readwise.io/read/01m7r30j7nvrcksj8cms1v2b09))
- On the Ollama side, we shipped the ability to connect your favorite harness through the `ollama launch` command. So you can connect harnesses like Claude Code, Codex, Pi (and more) with open models like DeepSeek-V4.1-Flash and GLM-5.3 and maintain your existing workflows. ([View Highlight](https://read.readwise.io/read/01m7r312ejfnxxzdqbp6p1vaba))
- Connecting a harness to an API might seem easy, but there are many layers of translation and varying expectations between a harness and a model. This often is the cause of cache breakages (incurring time and monetary costs), unexplainable agent behavior, and the harness outright erroring. ([View Highlight](https://read.readwise.io/read/01m7r314ca3ajez20mnmxr38kc))
- Harnesses carry quite a few tools now. If every definition goes into the prompt up front, you spend context on tools the task will never use, and the model gets worse at picking the right one. Newer harnesses have added a feature for tool search to alleviate this, where the tool can be loaded and used by the agent itself after searching for it. ([View Highlight](https://read.readwise.io/read/01m7r31ezf1z91zd4g1882tybp))
- Let’s say you have a personal assistant as an agent which has this capability. If you ask the agent to export the events you've starred to a calendar, and it searches for "calendar," loads the `save_calendar` definition, and calls it. ([View Highlight](https://read.readwise.io/read/01m7r31h6drj3gjqnnamne60hz))
- ![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6af7a33a50a1e098dee56917_Image%205.webp) ([View Highlight](https://read.readwise.io/read/01m7r31ngwnc53vnf8f850708d))
- The obvious approach is to add the definition to the tool list. That works, but the tool list sits near the top of the prompt, before the conversation. So if the prefix changes everything after it gets processed again. On a long session, that can be hundreds of thousands of tokens. The better approach is to put the definition at the end, where new content goes anyway. ([View Highlight](https://read.readwise.io/read/01m7r31qf9e4v2k2gd5d2p5ycm))
- Except not every model supports that. Some chat templates don't expect a tool definition halfway through a conversation, and the call errors out. So whether a harness can load tools late without paying for it depends on the model. Users shouldn't have to know this, but anyone building a harness does. ([View Highlight](https://read.readwise.io/read/01m7r31rvf9b62wg36tx3pzacq))
- The easiest way to wreck the cache is to put something in the system prompt that changes from turn to turn, like a current timestamp, the git status, or a working directory the agent keeps moving through. If the harness re-renders the system prompt with fresh values on every turn, every turn is a full re-read. ([View Highlight](https://read.readwise.io/read/01m7r31w1spx6vm4831s11kwc4))
- Things that are fixed for a session but differ between sessions, like the user's name or the date the session started, don't hurt that session. They do stop new sessions from reusing a setup that's already cached, which we'll get to on the engine side. Either way, the fix is the same: put that information in the task message, once, and keep the system prompt identical everywhere. ([View Highlight](https://read.readwise.io/read/01m7r32419x9z80yygc51n8te9))
- We hit this one on the Ollama side. In GLM-5.3-Flash, reasoning effort isn't a separate setting the engine handles on the side. The chat template writes it into the very first system block, ahead of the tools and the conversation. ([View Highlight](https://read.readwise.io/read/01m7r32jx61smwpg4agsdmtek2))

- Let’s say you're deep into a long task and it isn't going well. You raise effort from low to high. That's a reasonable thing to do, but the next request now differs from the last one almost at the first token. Which means the whole session gets processed again. On a long run, that can be hundreds of thousands of tokens spent on changing one setting. ([View Highlight](https://read.readwise.io/read/01m7r32tc69840mtzpkn6kby35))
- Our advice is to pick an effort level at the start and leave it there. If you really need more thinking, it's often cheaper to start a fresh session at the higher setting than to continue the old one, and you get a clean context out of it too. You could also compact before changing the reasoning value to decrease the amount of prompt tokens. ([View Highlight](https://read.readwise.io/read/01m7r32vr0qvsbwhxd9xxvzvth))
- A tool’s output becomes part of the next request, and of every request after it. If the agent reads a 3,000-line file when it needed forty lines, you don't pay for that once; you pay for it on every remaining turn (even if it is cached you lose out on the context window). To combat this, harnesses often cut tool output down. That's the right call, but how you cut tool output matters. ([View Highlight](https://read.readwise.io/read/01m7r32xf6y7vchg5g3dbxs2dp))

- Here's a failure that's easy to build by accident. The task is to fix a timezone bug in a calendar export. The agent reads `calendar.py`, and the tool returns the first 100 lines of a 640-line file without saying it stopped. The function that matters, `convert_timezone`, is at line 420. The model has no idea it's missing anything. ([View Highlight](https://read.readwise.io/read/01m7r330b8n1z4x5a3v1zfqk76))
- The fix is a single line in the output, telling the model it got lines 1 to 100 of 640 and that it can search the file or request another range. With that, the model searches for "timezone," finds line 420, and reads lines 410 to 450. Cutting output saves money. Cutting it without saying so gets you a model confidently editing code it never saw. ([View Highlight](https://read.readwise.io/read/01m7r332t9ygkq4gf4gka1z5cs))
- Open models like Kimi K3, GLM-5.3, and GLM-5.3-Flash are now pretty good at splitting a big task and handing pieces to subagents. How the harness starts each subagent decides how much of the parent's cache it can reuse. ([View Highlight](https://read.readwise.io/read/01m7r33624tdn5qq4pvsxktnyc))
- ![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6af7a43a91420901cc5f7063_image%208.webp) ([View Highlight](https://read.readwise.io/read/01m7r3371m288j77pstes2qj3q))
- One option is for the subagent to inherit everything: the same system prompt, tools, and conversation, plus its assignment. Side chats work this way. They branch off the parent session, so the whole prefix is already cached. The other option is to send a brief: the same system prompt and tools, then only the files and instructions the subagent needs. In that case the cache covers the setup and nothing more. ([View Highlight](https://read.readwise.io/read/01m7r339rrwyvzj8y9pxgcx79t))

- A session's cache lives on a particular node in a particular data center. If the next turn in a conversation lands anywhere else, that node has to process all earlier turns from scratch, and now two nodes are storing the same prefix. In order to route correctly we First need to pick a data center that runs the model, has capacity, and is where the session has been running. Then we need to pick a node inside it that has the previous turns cache. ([View Highlight](https://read.readwise.io/read/01m7r33j3yp41fncwew3ktm8e9))
- There are two main ways to pick the node. The simple one is to use a key: the client sends something like `prompt_cache_key` with every request and then ideally we route every request with the same key to the same node. The other way is to hash the prefix and send the request to whichever node has the longest matching prefix cached, even if another session put it there. ([View Highlight](https://read.readwise.io/read/01m7r33jymjf9gd6tdxm9gjg62))

- It also isn't as simple as always sending the request to the warm node. Sometimes the warm node is overloaded with traffic, and then the choice is between waiting in line there or taking an idle node and paying to process the prefix again. In this load-aware routing paradigm sometimes the cache miss might be the better deal. So even a perfectly stable prompt doesn't guarantee a hit if the infernce engine on the backend is not implemented correctly. - Routing only helps if there's still a cache to route to. An agent will often make a tool call and then wait a couple of minutes while tests run. Keeping that session's cache in GPU memory the whole time takes space active users need, and throwing it away means re-reading everything when the agent comes back from its tool calls. So we can also offload the cache to CPU memory while the session is idle and restore it for the next turn. ([View Highlight](https://read.readwise.io/read/01m7r33v49tgke87hkj4mnj04x))

- Memory is the constraint behind most of this. We can't know ahead of time whether a response will be 30 tokens or 30,000, so instead of reserving room for the worst case max context length scenarios, we hand out cache memory in small blocks as each request needs them (PagedAttention), the way an operating system handles RAM. And we rebuild the running batch on every pass (continuous batching), so when an agent fires off five subagents at once, each new request takes a slot the moment one frees up instead of waiting for the slowest one in a batch to finish. ([View Highlight](https://read.readwise.io/read/01m7r340rvd9m1shwzgvpc85yz))
- The upshot for anyone building a harness is that headroom for cache memory, not compute, is usually what limits how many requests a GPU can serve at once. Every oversized tool result, and every subagent carrying irrelevant history takes memory that another session's cache could have used. ([View Highlight](https://read.readwise.io/read/01m7r342tvemkj9x267m80qwsg))
- Agents also push the prefill/decode split to its extreme, with enormous prompts and tiny answers. To better optimize this we run the two phases on separate clusters. One is tuned for compute and does prefill; the other is tuned for memory bandwidth and does decode for hundreds of streams at once, with the cache shipped between them over RDMA. That way, a wave of long agent prompts doesn't slow token streaming for everyone else. ([View Highlight](https://read.readwise.io/read/01m7r344bjpeaanf85xtat4m7z))
