The idea was that having a test for each distinct behavior would guide the LLM in arbitrating a solution. But interacting with the LLM throughout the TDD cycle was too granular to be effective—particularly without any sort of built-in IDE support. - After discarding my purist TDD interests, I decided to brainstorm a better approach to *AI-assisted development*, one that also heavily involved using tests to *verify* the generated code. ([View Highlight](https://read.readwise.io/read/01jvt96hrbb7g5nyc0wxw2jet9))
- I could get an LLM to produce correct solutions occasionally, given only a brief description of the problem. ([View Highlight](https://read.readwise.io/read/01jvt96qh64pg54cvgx0mc921n))
- When the LLM generated defective code, I was in all cases able to negotiate with the LLM to arrive at a correct solution. Sometimes this negotiation took over a half-dozen attempts, however, and sometimes it involved reconsidering the design. ([View Highlight](https://read.readwise.io/read/01jvt96tt81ap0hcnprkt5avja))
- I was able to have the LLM generate unit tests (as well as other kinds of tests), by prompting it with examples that described all the desired scenarios. Each example succinctly captured the expected output for a given set of inputs (or series of operations). The generated tests had high fidelity with the examples. ([View Highlight](https://read.readwise.io/read/01jvt96yerq7jkas1qsrne34ht))
- The LLM generated low quality code by default—procedural, unnecessarily complex, and with minimal abstraction [[1]](https://jjlangr.substack.com/p/squelching-bad-vibe-coding/#footnote-1-161683908) . ([View Highlight](https://read.readwise.io/read/01jvt97z15addszjtwa2h56hea))
- When providing the LLM with a set of design guidelines (such as “extract all small conceptual chunks to separate functions”), it produced higher-quality code, usually sufficient for my interests. ([View Highlight](https://read.readwise.io/read/01jvt98cm4s3f2e44csqm6p117))
- The LLM ignored some of the design guidelines from time to time. ([View Highlight](https://read.readwise.io/read/01jvt98fmv98t9x7p5dbha4e4d))
- Rather than generating code at the function level, focus on generating a complete, *single-responsibility,* *closed* class (or module). If I want to change the behaviors of a generated class, I regenerate it entirely. ([View Highlight](https://read.readwise.io/read/01jvt98pk9txmkkj6ektm0kdqw))
- Generate tests *at the same time as* the code, using a set of examples that comprehensively describes the module/class. Quickly vet these tests for fidelity with the examples. ([View Highlight](https://read.readwise.io/read/01jvt98v4zfbrm880nkmjztyqt))
- Provide a very small set of design guidelines (predominantly around promoting functional solutions with high abstraction) with each prompt. ([View Highlight](https://read.readwise.io/read/01jvt990wn1jshspaa1kndp3xv))
- Two big hypotheses also followed these initial insights:
  • Providing the LLM with examples improves [compliance](https://jjlangr.substack.com/p/an-aadv-glossary).
  • Providing the LLM with code/design guidelines improves compliance (in addition to improving the ability to negotiate when it generates a non-compliant solution). ([View Highlight](https://read.readwise.io/read/01jvt99796kmd5abxa0j2hd76y))
- Somewhere before mid-2024, I started building a process around this notion of **A**I-**A**ssisted **D**evelopment with **V**erification—AADV [[3]](https://jjlangr.substack.com/p/squelching-bad-vibe-coding/#footnote-3-161683908) . Its centerpiece is a technique I named **CAX**—**C**reate, **A**ssess, e**X**ecute—in which you use the LLM to generate both tests and code, assess the tests, then run them. You repeat the cycle until all tests pass when executed. ([View Highlight](https://read.readwise.io/read/01jvt9ahpgkg8s3ngma5hg1tct))
- The AADV process, still under development, consists of a prime directive, CAX, an in-flux set of design prompts, guidelines for creating examples (based off well-known testing principles), and an evolving design philosophy on creating “pluggable” systems. ([View Highlight](https://read.readwise.io/read/01jvt9avf03fpdh8cf39kg29m4))
- Think of it as “vibe coding with proper safeguards.” It’s not likely that you’ll succeed without some grounding in—or interest in learning enough about—good old-fashioned systems design and testing principles. ([View Highlight](https://read.readwise.io/read/01jvt9b0nbm509dvd41z4vr4w7))
- Delivering a sustainable system with AADV will continue to require your design skills. If the idea is to assemble a bunch of LLM-generated components to create that system, you must still understand how big a module should be (what set of responsibilities it should contain), what its public interface must look like, how to orchestrate logic to accomplish desired behaviors, and so on. ([View Highlight](https://read.readwise.io/read/01jvt9b69erjn1w3hzvx9dbyhy))
- The more I generate code with my LLM, the less I care what the implementation of my functions look like. Here’s old-school generated code to determine if a word is an *isogram* and thus does not contain repeated letters: ([View Highlight](https://read.readwise.io/read/01jvt9bp441r932pqwm220d2mh))
- But nowadays I don’t care much which generated implementation I land on, as long as it works. I don’t have to maintain the code within `isIsogram`. I *do* still need to concern myself with everything else in software development, such as modular design and performance. I also know I can trust `isIsogram` to do its job because I was following CAX. ([View Highlight](https://read.readwise.io/read/01jvt9ck184mabh0s0k3csbhw1))
- Having said all that, the implementation specifics *do* matter if it’s not right. When a sloppy solution isn’t compliant, I ask for a more-scannable (modern) implementation—something I can glance at and understand. ([View Highlight](https://read.readwise.io/read/01jvt9d3rpbsb7f3bk2ncgve8a))
- As someone who had found decades of joy in crafting what I believe to be elegant, highly-maintainable code, I’m surprised at what I’m promoting. With AADV, I’m indifferent to the inner workings of all the functions, and that’s OK. Nowadays I usually only quickly scan the innards of a module, mostly looking for anything that looks out of place. I don’t have the time to read all the implementation details [[5]](https://jjlangr.substack.com/p/squelching-bad-vibe-coding/#footnote-5-161683908) , and I don’t need to. ([View Highlight](https://read.readwise.io/read/01jvt9de6g82jzv07sb095yv0m))
- Today’s LLMs gorged themselves on massive piles of low-quality code: redundant, poorly structured, and lacking tests. As a result, the trillion-plus lines of AI-generated code to quickly come will exist in an equally large percentage of low-quality codebases. Are we doomed to the [ouroboros effect](https://en.wikipedia.org/wiki/Ouroboros) of LLMs eating their own tail, endlessly feeding on their own spewage? ([View Highlight](https://read.readwise.io/read/01jvt9et6wnda0ppd0jna7pak9))
- Make sure you read the title of this **AI Code Correct** post as “vibe coding that happens to have a bad outcome,” not as “vibe coding is bad.” ([View Highlight](https://read.readwise.io/read/01jvt9f8b7j81b6522cnyp34tf))
- Still, you know how things are: The label—or the vibe of the label—is often what sticks. Too many developers will do exactly what Karpathy is suggesting: Generate code with an LLM, look it over for defects, perhaps run a few manual tests, and ship it. ([View Highlight](https://read.readwise.io/read/01jvt9feg4yy2qps7g2e6k64nq))
- Unfortunately, too many of those developers won’t find enough defects in that process. “Vibe coding” will lead to an unnecessary backlash against AI coding [[8]](https://jjlangr.substack.com/p/squelching-bad-vibe-coding/#footnote-8-161683908) . ([View Highlight](https://read.readwise.io/read/01jvt9fnt05exwx4knwj4qr8rq))
- If you cross-section code quality with effective test coverage, you get what I’ve termed the *code* *integrity matrix*.
  [![](https://substackcdn.com/image/fetch/w_1456,c_limit,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F888e16db-e59d-4f72-8c3f-b0de395448d5_1342x1206.heic)](https://substackcdn.com/image/fetch/f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F888e16db-e59d-4f72-8c3f-b0de395448d5_1342x1206.heic) ([View Highlight](https://read.readwise.io/read/01jvt9ghr2px3p3dqrtpftzgwp))
- Perilous code: We shouldn’t ever ship low-quality, poorly-tested code. But we do. We might have been able to slap it out, but it will cost us increasingly dearly over time. ([View Highlight](https://read.readwise.io/read/01jvt9gmmjtrtbx2fknwwhn0hv))
- Unchecked code: We’ve invested time painstakingly crafting well-designed code without tests. While the better design allows us to more easily adapt the software, we’ll do so at a slow pace. ([View Highlight](https://read.readwise.io/read/01jvt9grckmx0y20vb04kkns35))
- Sustainable code: We’ve invested time to painstakingly craft properly-designed code and corresponding quality controls. Costs will remain reasonable as we continue to change the software. ([View Highlight](https://read.readwise.io/read/01jvt9gwhyjhvf10eavgybmkkr))
- Utilitarian code: We’ve invested time creating proper quality controls, but haven’t taken advantage of them to keep the code clean. Humans can safely change the code, but costs will be higher than for sustainable code. *This is the sweet spot for CAX, which allows rapid generation of both adequate-quality production code and high-fidelity automated tests.* ([View Highlight](https://read.readwise.io/read/01jvt9gz9nvxq24cv5vvfn1see))
- Maximal effective coverage exists when the tests verify all the behaviors intended by its developers. (It’s possible that your code coverage tool shows high coverage even when some features aren’t at all verified.) ([View Highlight](https://read.readwise.io/read/01jvt9h4fy69b3sfey3jpsyza4))
- Ultimately, your choice of code integrity quadrants is up to you. If you’ve determined that your customers / users are willing to accept perilous solutions, that’s your prerogative. Vibe coding alone will get you there. ([View Highlight](https://read.readwise.io/read/01jvt9h7ha1dreztwfnjme2g0t))
- Consider AADV + CAX as “vibe coding plus,” a simple and streamlined way to emanate positive vibes while letting your LLM create the implementation details. You’ll quickly produce trustworthy solutions that lie in the high part of the utilitarian quadrant. ([View Highlight](https://read.readwise.io/read/01jvt9hcehyb2xnq7b2hxyfdqh))
- *Low quality* here indicates code that’s hard to maintain. Code that doesn’t do what it’s asked is *defective* or *noncompliant*. ([View Highlight](https://read.readwise.io/read/01jvt9hjqymqc59z816apmw864))
